# 题库项目 · 面试讲解手册（知识点地图 + 预判追问）

> 用途：简历讲解 / 技术面深挖。**所有数字都来自本仓库实测**（见文末"数字台账"）。
> 定位：**LLM 应用工程 + 后端工程**（不是算法岗、不是高并发岗）。诚实边界见"不能说的三件事"。

---

## 0. 一句话定位（面试开场用）

> "一个人做了一套给自己用的备考刷题系统：**8,090 道题、4 个科目、7 个 SQLite 库**，
> 核心难点是**判分**——怎么让 75.8% 的题不花一分钱、当场判、还能落库统计；
> 剩下主观题才调 LLM，并且做了完整的成本闸门、失败重试和幂等回滚。
> 另外做了套卷模拟考、弱势诊断、和一条从真题网页抓取→清洗→去重→入库的数据流水线。"

三种可切换的侧重：
- 偏**后端**：讲 schema/状态机/写库契约/幂等/事务回滚/接口设计。
- 偏**AI 应用**：讲规则优先架构、prompt 版本化、mock、缓存死循环、成本账本、付费闸门。
- 偏**数据工程**：讲多源抓取、反爬、跨源去重、脏数据修复、数据质量度量。

## 1. 知识点地图（按领域，每条：是什么 / 用在哪 / 为什么重要）

### A. 架构与分层

| 知识点 | 是什么 | 用在哪 | 为什么重要（可讲的点） |
|---|---|---|---|
| **单一事实源（SSOT）** | 同类逻辑只允许一处实现，其他层调用它 | `scripts/judge_local.py`（规则判分）、`update_daily_progress.py`（对错阈值）、`lib/uid.py`（uid 生成） | Web 层与 CLI 层**共用同一套判定**，避免"页面算对了、统计算错了"的分叉。面试可讲：我曾有过两处各自判分导致统计不一致的教训 |
| **契约优先** | 先定"谁写哪张表、谁读哪张表"，再写代码 | `wrong_book` 只由 `sm2_scheduler` 写；`review_log` 只追加；`daily_progress` 只由聚合脚本覆盖写 | 多进程/多入口写同一张表是脏数据的根源。这是本项目最重要的一条设计 |
| **分层** | 数据层（scripts）/ 服务层（Flask）/ 展示层（原生 JS） | `app/backend/app.py` 只做复用与编排，不重写算法 | 让"判分口径"能脱离 Web 单独测试（17 个测试文件里有 12 个是纯脚本测试） |
| **可测试性设计** | 模块级路径常量可被 patch；纯函数优先 | `DATA/LOGS/OUTPUT` 都是模块级；`aggregate_rows()` 是纯函数 | 测试能把 `DATA` 指到临时目录，**不碰真实库**（关键：用户数据零污染） |

### B. 数据建模与 SQLite 工程

| 知识点 | 是什么 | 用在哪 | 为什么重要 |
|---|---|---|---|
| **宽表 + 可空列 + 后加列迁移** | 题目字段多且来源不一，用单表宽表；新列用 `ALTER TABLE ADD COLUMN` 幂等迁移 | `questions` 31 列；`init_db.migrate_questions()` | `CREATE TABLE IF NOT EXISTS` **不会补列** → 老库缺 `group_uid` 时接口直接 500。我加了幂等迁移并写进测试 |
| **枚举用 CHECK 约束** | 状态机取值在库层就约束住 | `questions.status` 六值、`judge_queue.judge_status` 四值 | 状态是业务核心，库层兜底比只在代码里校验可靠 |
| **多库分片（按科目）** | 每科一个 `.sqlite`，公共库单列 | `data/{english,c_wuhan,c_hbpu,aca_llm}.sqlite` + `attempts.sqlite` | 单文件可拷走、可按科备份/重建；代价是跨库聚合要在应用层做（诚实讲这个 trade-off） |
| **WAL + busy_timeout** | 写连接开 WAL，所有连接设 30s 超时 | `connect()` 全项目统一 | 网页在跑、脚本也在写，避免 "database is locked" |
| **只读连接** | 读接口用 `file:...?mode=ro` URI，且**不设 WAL** | `open_db(write=False)` | 改 `journal_mode` 会写库头文件 → 违反"只读接口零写盘"的契约（我写进了模块 docstring） |
| **索引** | 按查询模式建 | `status` / `knowledge_point` / `(subject, question_type)` / `judge_queue.created_at` | 8,000 题级别 SQLite 走索引后组卷/统计是毫秒级 |
| **幂等写入** | 同一天重跑结果一致 | `INSERT ... ON CONFLICT(date) DO UPDATE`（daily_progress）；`INSERT OR REPLACE` | 全量重算比增量累加安全：回改一条作答，重算就对，不用撤销历史增量 |

### C. 状态机与一致性（**最能讲深的一块**）

| 知识点 | 是什么 | 用在哪 | 为什么重要 |
|---|---|---|---|
| **判分四态机** | `pending → submitted → synced / failed` | `judge_queue.judge_status` | 用户提交时**先落库再判分**，进程崩了作答不丢；`failed` 可手动重投（我实现了 `/api/requeue`，支持 `force`） |
| **事件源 vs 物化视图** | `review_log` 是**只追加的作答事实流**；`wrong_book` 是由它推导出的"复习状态" | `sm2_scheduler.py` | 事实与状态分离 → 重放事件就能重建状态。这是本项目最值钱的概念 |
| **水位（watermark）去重** | 用 `wrong_book.updated_at` 记录"处理到哪个时间点"，只处理 `reviewed_at > updated_at` 的事件 | `sm2_scheduler.process_subject()` | 让"重放事件"幂等：跑 100 次不会把错题计数翻倍 |
| **🔴 单写者原则 + 一次真实 P0** | `wrong_book` 只允许 SM-2 调度器写 | `sync_outbox.write_back()` 里明确注释"绝不写 wrong_book" | **故事**：早期判分脚本也写 `wrong_book` 且把 `updated_at` 设成事件同一时刻 → 水位判据 `reviewed_at > updated_at` 把该事件永久判为"已处理" → **所有答错事件永远不会被 SM-2 处理**（复习功能静默失效）。修法不是加判断，而是**取消第二个写入者** |
| **失败必须回滚** | 重试过程中已经写了一半的 `judge_score`/`synced=1`，失败时要 `rollback()` 再标 `failed` | `sync_outbox.run()` | 否则出现"状态 failed 但分数非空、synced=1"——下游误判为"已判分"，是典型的**半成品状态泄漏** |
| **恢复中间态** | 消费 `pending` 的同时也消费 `submitted` | `judge_queue` 查询 | 进程在 `submitted` 阶段被杀，这些行本该是"待判"，只认 `pending` 会让它们**永久卡住** |

### D. Web 后端与 API 设计

| 知识点 | 是什么 | 用在哪 | 为什么重要 |
|---|---|---|---|
| **本地优先（local-first）的写路径** | 提交时**当场规则判分并落库**，判不了才进 AI 队列 | `POST /api/submit` → `apply_local_verdict()` | 直接解决了"首页今日进度永远是 0"——因为以前每题都等 LLM 出分才算 |
| **付费闸门（paid gate）** | 会花钱的接口必须显式传 `confirm_paid=true`，否则 400 | `/api/sync`、`/api/judge_one`、`/api/weakness/advice` | 演示/误点不能烧钱。这是产品化的安全设计，不是技术炫技 |
| **REST 语义与错误码** | 400 参数错 / 404 资源不存在 / 500 内部错 / **501 功能未接通** | 各接口 | 后端未实现的功能用 501 明确告知，而不是假装成功或 500 |
| **CORS 与本地收集口** | 浏览器从第三方页面直接 POST 到本机接口落盘 | `POST /api/ingest` | 让 144 道抓取数据**不经过模型上下文**（省 token 且准）。同时做了边界：文件名白名单正则、单批 ≤2000 条、只写 `inbox/_ingest/` |
| **密钥永不回显** | 只回 `api_key_configured` + 掩码 `sk-…f393` | `/api/settings`、`mask_secret()` | 页面/日志都拿不到完整 key |
| **配置写入校验** | 键名正则、值禁止换行/NUL、长度上限 | `write_env_value()` | 防注入（一行 `\n` 就能把别的配置顶掉），且保留原 `.env` 注释与其余行 |
| **超时与子进程** | 外部脚本用 `subprocess` + 超时（900s/300s），输出 UTF-8 | `/api/sync`、`/api/judge_one` | 长任务不能把 Flask 请求挂死 |
| **端口协商** | 5000 被占回退 5001，实际端口写 `app/port.txt` | `app.py:main()` | 验收脚本必须读 port.txt，不能硬编码——这条我写进了约定，并因此踩过坑（见 E2E 测试） |

### E. 判分系统工程（规则引擎）

| 知识点 | 是什么 | 用在哪 | 为什么重要 |
|---|---|---|---|
| **"宁放不误"（precision over recall）** | 拿不准就**不判**，交给 AI/人工，绝不猜 | `judge_local.Verdict(gradeable=False)` | 判错**对**的代价远大于不判：会污染 SM-2 复习排程和正确率 |
| **规范化管线** | NFKC 全角转半角 → 标点映射 → 去答案标签前缀（`【答案】`/`空(1)处填：`）→ 折叠空白 → 小写 → 去句末标点 | `normalize_text/compact/tokens` | 用户输入"换行/空格/全角标点"不该被判错。三档规范化各有用处（保空白/抹标点/全抹） |
| **题型分派 + 逐级回退** | 先按题型走专用判定；判不了再按"答案形态"回退（纯字母/是非值/短文本） | `judge_local()` | 数据脏（题型标错）时仍能尽力判对，但每级回退都要求形态吻合 |
| **多空题识别** | 答案字段塞了整份卷子多个空（`"A | C | D"`）→ 拒绝判分 | `is_multi_blank()`（空标记 + 备选形态） | 这是**数据形态**问题，不是判分逻辑能解决的，硬判必错 |
| **闸门（guards）** | 长度上限、题干内嵌选项可信度（含"正确/错误/不是"就丢弃） | `MAX_TEXT_LEN=80`、`options_from_stem()` | 论述题混进填空题、题干正文被正则吞进来，都要靠闸门挡住 |
| **探针式自测（probe test）** | 把题库**自带的每个备选答案**当作答喂进去，凡"答对却算错"即为过严 | `judge_local.py --coverage` | 没有标注数据也能度量误判。**这个思路比测试用例更狠**：它自动扫全库 |
| **误报率意识** | 我加过一条"解释里没提到答案字面"的判据，它把 **59.7%** 的真题标成可疑，全是误报 → 删除 | `audit_explanations.py` docstring | 一个"狼来了"的判据会让整个报告失去信任。宁可少报，不可乱报 |

### F. LLM 应用工程

| 知识点 | 是什么 | 用在哪 | 为什么重要 |
|---|---|---|---|
| **规则优先，LLM 兜底** | 能用确定性逻辑解决的绝不调模型 | 75.8% 走 `judge_local`，剩余走 LLM | 成本、延迟、稳定性三赢。这是本项目最核心的工程判断 |
| **Prompt 版本化** | `judge_prompt.json` 带 `version`，判分结果写 `judge_prompt_version` | `sync_outbox.build_messages()` | 换 prompt 后能按版本回溯"这批分是哪个版本判的" |
| **少样本注入（few-shot）** | 从真题参考库取同题型样例（带出处/可信度）拼进 prompt | `validate_and_fill.few_shot()` + `build_reference.py` | 生成质量的关键。**注意：这不是 RAG**（无向量检索），是静态参考库 + 分层取样 |
| **分层取样 + 确定性** | 按 `official_exam > textbook > third_party` 分层，再按 `exam_title` 轮转，**不用 `ORDER BY RANDOM()`** | `build_reference.pick_samples()` | 保证同一份库每次构建结果一致，可复现（面试可讲"可复现构建"） |
| **🔴 缓存命中导致死循环** | 少样本是确定性的 → prompt 每一步完全相同 → 上游 KV cache 命中且模型"没话说" → 空转不产出 | `validate_and_fill.py` 的修法 | 修法：**每批轮换聚焦一个知识点**，让 prompt 必然变化。这是很真实的 LLM 工程坑 |
| **Mock 判分** | 不联网的确定性启发式，用于链路自检 | `sync_outbox --mock`、`/api/sync?mock=true` | **坑**：mock 必须**按该题型满分折算**，否则 2 分题的满分刻度下英语题永远判错（早期真实 bug） |
| **没有 Batch API 的应对** | 实测官方 `/batches`、`/v1/batches`、`/beta/batches` 全 404 | `sync_outbox.py` docstring | 只能**串行** `chat/completions`；`judge_status='submitted'` 的语义退化为"已进本地串行队列" |
| **重试与退避** | 失败重试 3 次，1s/2s/4s；仍失败标 `failed` 可手动重投 | `sync_outbox.run()` | 区分"暂时性失败"与"数据缺失"：题目查不到 → **直接 failed**，重试没意义（早期把两种情况混在一起，产生过相反语义） |
| **推理档位** | 判分用 `low`（省思考 token），写作/编程用 `high` | `reasoning_effort`、`taxonomy.judge` | 不同任务用不同思考深度，是成本控制的一环 |

### G. 成本与配额控制（AI 应用岗高频追问）

| 机制 | 实现 | 作用 |
|---|---|---|
| 逐次账本 | `logs/cost_ledger.jsonl` 每调用 append（模型/usage/估算成本） | 事后可审计"钱花在哪" |

### H. 数据获取与反爬

| 知识点 | 是什么 | 怎么做的 |
|---|---|---|
| **JS 机器人挑战识别** | Node 直连拿到的是 ~987 字节混淆脚本（设置 cookie 后 `location.replace`） | 判断"不是页面 → 是挑战页"，改用**浏览器页面内 fetch**（自然带上挑战写入的 cookie） |
| **Nuxt SSR 数据提取** | 数据在 `window.__NUXT__`，载荷是**函数调用**而非纯 JSON | 写**括号配平切表达式**（跳过字符串内部）+ 在隐藏 iframe 里 `eval` 得到对象。DOMParser 不行（不执行内联脚本） |
| **分页发现** | 分页不是 `?page=` 而是 `/ti/<id>/p_2.html` | 从 DOM 里读 `href` 得出真实规则，8 页 × 20 = 144 题 |
| **数据不经过模型** | 144 题若走模型上下文会吃掉大量 token | 页面内 POST 到本机 `/api/ingest` 直接落盘（CORS + 白名单 + 批次上限） |

### I. 数据质量工程（**这套项目最像"真实工程"的部分**）

| 问题 | 诊断 | 修法 |
|---|---|---|
| **来源标注缺失** | 919 条 `trust_level` 为 NULL（英语 707 / c_wuhan 64 / c_hbpu 64 / aca 84） → 来源徽标画不出来 | `fix_trust_level.py`：按**证据分级**推断（`source_type='generate'` → AI；`real_exam`/`exam_title` 含年份省份 → 真题；`source_url` 命中第三方域名 → 第三方）；**无证据不猜**，保持 NULL |
| **模板残留题** | 6 道题题干就是"请输入题目内容 / A. 选项内容"、答案 A、解释"请输入解析" | 下架（`status='rejected'`），刷题池 5,764 → 5,758。**判据只看题干特征**——我第一版把"解释为空"也当判据，差点误下架 692 道正常题 |
| **源字段丢失** | 369 道英语客观题没选项，题面只有 `It is essential that every student ___ a library card…` | 定位到导入脚本漏读 `item.interaction.choices`；新脚本按 `group_uid` 回补 **452 道**；剩 115 道原始素材就没有（不可恢复，如实统计） |
| **解释可信度** | 6,673 条真题解释 | 只认"确定性硬伤"（过短/占位符/与答案一字不差/答案为空）→ **33 条 = 0.5%**，已修 |
| **跨源重复** | 同一道题从两个站点抓到，`uid` 因含 `source_url` 而不同 | 二级指纹 `content_fingerprint`（归一化题干 → sha256），查重命中 15 道 |
| **选项列全空** | 全库 `questions.options` 一条都没有值 | 运行期 `runtime_options()`：先看 `options`，空则从题干解析（带安全闸门），再空则退回填空题渲染——**不编造选项** |

### J. 算法与启发式

| 知识点 | 是什么 | 用在哪 |
|---|---|---|
| **SM-2 间隔重复** | 按答题质量调整间隔，本项目档位 `[1,3,7,14,30]` 天，答错"退一档" | `config/sm2_config.json` + `sm2_scheduler.py` |
| **折叠事件 → 状态** | 按 `(reviewed_at, id)` 顺序重放事件算出 `correct_streak/mastery/next_review_at` | `process_subject()` |
| **分层聚合 + 低样本抑制** | 按科目/知识点/题型分桶算正确率；`judged < 3` 标 `low_sample` 不进弱势榜 | `weakness.py`（`MIN_SAMPLE=3`、`WEAK_RATIO=0.6`） |
| **覆盖率与缺口** | "题库有多少 / 我做过多少"，并按知识点算"未刷题最多"的前 3 | `weakness.coverage()` |
| **哈希指纹** | `sha256(subject:source_url:stem[:50])[:16]` 做 uid；`sha256(subject:归一化题干)[:16]` 做跨源指纹 | `scripts/lib/uid.py` |

## 2. 预判追问 25 问（附标准答法）

> 原则：先给结论，再给**证据/数字**，最后给"取舍"。答不出就说"这块我没深入，我当时的做法是 X"。

**Q1 为什么用 SQLite 不用 MySQL/Postgres？**
单机、单用户、离线优先、数据要能"整个拷走"。8,000 题规模 SQLite 完全够（索引后毫秒级）。代价是并发写弱——我用"单写者 + WAL + busy_timeout + 重算幂等"来规避。如果上多用户，我会换 Postgres 并把串行判分队列换成 worker。

**Q2 每个科目一个库，跨库统计怎么办？**
统计在应用层遍历各库聚合（如弱势诊断、覆盖率）。代价是多库一致性没有事务保证——所以**只有 `attempts` 是唯一跨科目的写入点**，科目库只写 `review_log`。

**Q3 判分为什么两条通道？边界怎么定？**
边界是"答案是否唯一可机判"：客观选择/是非/填空/连词成句/C 短输出 → 规则；写作/整段翻译/论述题/要求写整段代码 → LLM。判定逻辑集中在 `judge_local` 的分派 + 闸门里，**拿不准返回 `gradeable=False`**。

**Q4 规则判分怎么防误判？**
（1）"宁放不误"：不确定不判；（2）**探针测试**：把题库自带的每个备选答案当作答，凡"答对却算错"即过严 → 当前 **0 条**；（3）针对踩过的三个坑写回归：`"D. great"` 不能被抽成 `"ADEG"`、`"A | C | D"` 是多空题要拒判、多选 `"ABD"` 必须能识别。

**Q5 那 24% 判不了的是什么？**
写作、整段翻译、论述题、要求"编写函数"的整段代码、一道题多空的完形、以及题库本身没答案的采集残题（ACA 有 168 条答案为空）。这些不是规则不够聪明，是**题目形态决定了不能机判**。

**Q6 为什么不用 Batch API？**
实测三个路径全 404（`/batches`、`/v1/batches`、`/beta/batches`）→ 只能串行。`judge_status='submitted'` 的语义就退化成"已进本地串行队列"。

**Q7 缓存命中死循环是什么？怎么发现？**
少样本是确定性的 → 每批 prompt 完全相同 → 模型输出被缓存/无新信息 → 空转不产出。修法：**每批轮换聚焦一个知识点**，prompt 必然变化。这是我实际踩到并修掉的。

**Q8 怎么控制 LLM 成本？**
结构性（75.8% 走规则）+ 机制性（逐次账本、`--cap-cny`、预算 warning/stop 线、mock 默认、`confirm_paid` 闸门、判分用 `low` 档、串行不并发放大）+ 产品性（强化方案默认只回 prompt、不自动调用）。

**Q9 Mock 判分有什么坑？**
必须**按该题型满分折算**。早期 mock 直接返回 0~1 比率，而英语 per_item 是 2/3/10 → `--mock` 下英语题**永远判错**（全对也才 1.0），同一语义出现两种结果。

**Q10 判分四态为什么要有 `submitted`？**
原意是"已提交到远端批处理"；没有 Batch API 后它表示"已进本地串行队列"的中间态。保留它是因为**进程在中间态被杀**时这些行仍应被处理——所以消费时 `pending` 和 `submitted` 都取。

**Q11 重试怎么做的？为什么一定要 rollback？**
重试 3 次、1/2/4s 退避；仍失败先 `rollback()` 再标 `failed`。不 rollback 会把重试中的半成品（`judge_score` 非空 + `synced=1`）一起提交 → 下游误判"已判分"。这是被独立测试抓出来的 P1。

**Q12 为什么 `wrong_book` 只能有一个写入者？（**最值得讲的一题**）**
`wrong_book.updated_at` 是 SM-2 的事件水位，判据是 `reviewed_at > updated_at`。如果判分脚本也写它、并把 `updated_at` 设成事件同一时刻，那么该事件下一轮就被判为"已处理" → **所有答错事件永远不会被 SM-2 处理**，复习功能静默失效。所以修法不是打补丁，而是**取消第二个写入者**：`review_log` 是唯一事实源，`wrong_book` 是它推导出的物化状态。

**Q13 `review_log` 和 `wrong_book` 的关系？**
事件源 vs 物化视图。前者只追加（question_uid, reviewed_at, result），后者由调度器按事件折叠出 `correct_streak / mastery / next_review_at`。好处：能重放、能审计、能改算法后重建。

**Q14 `daily_progress` 为什么全量重算不增量累加？**
增量累加在"回改历史作答"时会算错，且双写容易冲突。全量重算是幂等的：`ON CONFLICT(date) DO UPDATE`，同一天跑 N 次结果一致。

**Q15 时区怎么处理？**
库里存 UTC ISO 时间戳；聚合时按**本地自然日**过滤（先按 `substr(created_at,1,10)` ±1 天粗筛，再在 Python 里精确换算），覆盖各种时间戳写法（带时区/无时区/空格分隔/只有日期）。

**Q16 主观题分数怎么归一化？**
`<=1` 视为已归一化原样用；`>1` 除以该题满分并裁剪到 `[0,1]`；通过线 0.8。ACA 例外：满分即正确线（2 分），因为是本地规则判分。

**Q17 满分从哪来？为什么要小心？**
`config/taxonomy.json` 的 `per_item`（语法填空 2 / 翻译填空 3 / 写作 10 / ACA 2），ACA 还读 `aca_rules.json`。**早期把满分写死成 `{aca:2, writing:10, 其余:1}`，结果 2 分题得 1 分也被记 correct**——所以现在三处（判分、Web、聚合）共用同一套读取逻辑。

**Q18 套卷的"原卷顺序"怎么解决？`no` 字段没入库啊。**
实测发现**同一 `exam_title` 下题目 `id` 完全连号（断点 = 0）**，因为导入是逐题 append 的 → `ORDER BY id` 就是原卷顺序，**不需要补 `no`**。这是"先看数据再设计"的例子。

**Q19 套卷"看到 300 题、只判 200 题"怎么发现的？**
子任务并行时被独立验证方抓出来：C 语言有 448/454 题的巨卷，`/api/paper` 用 300、`submit` 内部默认 200。修法：两处统一用同一个上限常量，并在响应里返回 `limit_applied` / `truncated` 让前端如实提示。

**Q20 爬虫遇到 JS 机器人挑战怎么办？**
先判断"拿到的是不是页面"：Node 直连返回 ~987 字节混淆脚本（设 cookie 后 `location.replace`）。改用**浏览器页面内 fetch**（自然带 cookie），数据在 `window.__NUXT__`。它不是纯 JSON 而是**函数调用**，且后面跟着 HTML → 写**括号配平切表达式**（跳过字符串内括号），在隐藏 iframe 里 `eval` 取出对象。DOMParser 不行，因为不执行内联脚本。

**Q21 跨源去重怎么做？**
`uid` 含 `source_url` → 同一题两源会得到两个 uid。所以加二级指纹：`sha256(subject:归一化题干)` 前 16 位（NFKC + 去空白标点 + 小写）。用它查重，实测命中 15 道（含 `（）` vs `()`、`—` vs `-` 这种差异）。

**Q22 来源标签缺失怎么办？**
按**证据分级**推断：`source_type=generate`/`fact_source` 含 AI → AI 生成；`real_exam` 或 `exam_title` 含年份省份 → 真题；`source_url` 命中第三方域名 → 第三方。**无证据保持 NULL，不猜**。919 条全部落地，全库 0 条未标注。

**Q23 "解释只在真题显示"怎么做才不散落？**
单一入口 `explanation_policy(trust_level)`，三个接口（questions/reveal/judge_one）都挂同样的 `show_explanation/explanation_source/explanation_hidden_reason`；前端字段缺失时**按旧行为显示**（优雅降级）。另外：**本来就没有解释的题不显示"已隐藏"**——否则 692 条无解析的题会告诉用户"我们藏了东西"，是误导。

**Q24 解释正确性怎么验证又不烧钱？**
先做**零成本预筛**：只认确定性硬伤（过短/占位符/与答案一字不差/答案为空）→ 6,673 条里 33 条（0.5%）。同时我做了一次"误报率"复盘：曾加过"解释没提到答案字面"的判据，它标出 59.7% —— 全是误报（多空题答案是多空挤一行、C 科解释用定义论证），于是删除。**判据的价值 = 命中率 × 信任度**。

**Q25 依赖从 77 个砍到 13 个，凭什么？**
AST 扫全项目 import 打表；`pip download` 看真实体积（`ziglang 345MB` / `sympy 66MB` / `onnxruntime 35MB` / `pandas 34MB` / `numpy 23MB` 全是 0 引用）；再用**隔离验证**证明没删错：`-S` 不吃 site-packages 起服务，**15 个接口全 200、19 个脚本全 import 成功**。结果：wheel 从 500+ MB 降到 37.2 MB，离线安装 26.8 秒。

**（备选）Q26 API key 怎么存的？安全吗？**
写项目根 `.env`，**接口只回掩码**，从不回显完整 key；写入前校验（键名正则、值禁换行/NUL、长度上限）；前端 `type=password` 且**只有点按钮才保存**（无 oninput/onblur 自动保存），清空要二次确认。

**（备选）Q27 前端怎么防 XSS？**
不用 innerHTML 拼数据，统一 `textContent` / `TKU.esc()`。实测把 `<script>` 作为选项文本插入，页面不执行。另外页面零外链（无 CDN），既安全又可离线。

**（备选）Q28 为什么不做微服务/Redis/消息队列？**
单机单用户，SQLite 表就是队列（`judge_queue` 四态 + 串行消费），Redis 只会增加运维面。如果要做多用户/高并发：Postgres + 任务队列（Celery/RQ）+ worker 水平扩展 + 判分结果幂等写回。

**（备选）Q29 你怎么验证自己没污染用户数据？**
每个测试在临时目录建库并 patch 模块级路径；契约断言 `wrong_book` 一行未写、`questions` 表未变；e2e 最后一步做"前后快照相等"；冒烟脚本跑完按 `id` 差值精确删除自己写的行。

**（备选）Q30 这个项目最大的技术风险是什么？**
判分口径分叉（多处各写一套）和写库争抢（多个写入者）。我用"单一事实源 + 单写者契约 + 全量重算幂等 + 探针测试"三件事把它压住。其次是数据质量（缺选项/缺来源/错题型），我的原则是**能证据化就修、不能就如实暴露给用户**。

## 4. 不能说的三件事（面试被追问会翻车）

1. ❌ **别说"我做了 RAG / 向量检索"**。本项目是**静态真题参考库 + 分层取样拼 prompt（few-shot）**，没有 embedding、没有向量库、没有检索打分。正确表述："LLM 少样本生成 + 判分，参考库按可信度分层取样"。
2. ❌ **别说"高并发 / 分布式 / 微服务 / 用户量"**。它是单机单用户本地系统，并发模型就是 SQLite + 单写者 + 串行队列。正确的亮点是"**并发安全的写入契约**"，不是"高并发"。
3. ❌ **别说"全是手写"**。你选的是"主导 + AI 辅助编码"，就按这个说：需求拆解、架构与契约设计、数据治理判据、验收与回归测试是你做的；编码有 AI 参与，但**每一处都经过评审与测试**。面试官更认可这种诚实，且你能讲清每个决策的取舍。

## 5. 简历要点（3 条，按岗位微调）

- **判分系统**：设计"规则优先 + LLM 兜底"两级判分，把 75.8%（6,031/7,961）题目变为零成本、当场出分；用"全库探针"验证"答对不能判错"为 0 误判，覆盖客观选择/是非/填空/连词成句/C 短答案。
- **数据一致性**：以 `review_log` 为唯一事件源、`wrong_book` 由 SM-2 单写者维护，修复"双写导致复习事件永久失效"的 P0；判分失败强制回滚半成品，进度聚合采用幂等全量重算。
- **数据流水线**：完成真题网页 → 清洗 → 跨源去重（sha256 归一化指纹）→ 入库 → 质量体检的流水线；识别并修复 369 道"无选项"题（回补 452 道）、919 条缺失来源标注，用确定性判据把 6,673 条解释的可疑率压到 0.5%。
- （可选第 4 条，偏工程效率）**交付与效率**：依赖从 77 包瘦身到 13 个直接依赖（wheel 500+MB → 37.2MB），预置离线包使安装从数分钟降至 **26.8 秒**，并用 `-S` 隔离环境验证 15 个接口、19 个脚本无回归。
